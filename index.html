Executive Summary

三句话说完这套方案

01

一次接入，三类数据

业务只需要加两行 annotation。探针自动注入，Trace / Metrics / Logs 全部走同一个 OTLP 协议汇入，不再为每种信号维护一套 agent。

Trace Metrics Logs
02

分层采集，各管一段

应用侧管链路、节点侧读日志与容器指标、集群侧读对象状态。每一类指标只保留一条采集路径， 不与现有 Prometheus / node-exporter 重复采集。

应用 → 探针 / SDK
节点 → DaemonSet 读 CRI 日志
集群 → k8s_cluster · Events

统一出口，边界清楚

Gateway 统一补全 K8s 身份、脱敏、按 traceID 路由；尾采样看完完整链路再决定留或丢。 平台不装存储与看板，只负责把数据可靠地交给既有后端。

Gateway ×2 · Sampler ×2 · Scraper ×2

The Three Pillars

三要素，回答三个不同的问题

它们不是三套系统，而是同一批请求的三种投影 —— 靠 trace_id 与 span_id 互相点得动。

Trace · 调用链

一次请求跨了哪些服务、每一跳花了多久、在哪一跳失败。traceID 串起全部 span，父子关系还原真实调用树。

回答：慢在哪一跳？错在谁身上？

Metrics · 数值趋势

计数、耗时分布、CPU / 内存、对象状态。每 30–60 秒一个点，用于看趋势、做容量与告警。

回答：整体健康度如何？还剩多少余量？

Logs · 事件原文

应用 stdout / stderr 与 Kubernetes 事件。解析出原生 trace / span 字段后，日志可以一键跳回链路。

回答：当时到底发生了什么？

注意 日志里出现 ERROR 不等于 span 状态是 ERROR；HTTP 200 的业务失败也不会自动标红 —— 这两件事必须在埋点里主动标记。

应用侧

不改代码 · 不改镜像 · 只加 annotation。Go 等无自动注入的语言用 inject-sdk 提供环境变量，由代码初始化 SDK。

Architecture

总体架构：一条流水线，五个角色

每个集群独立一套 · cluster_name 唯一 · 可共用一个后端
One Request, End To End

一次请求的完整旅程

trace_id 4bf92f3577b34da6a3ce929d0e0e4736 6 个 span · 同一条 trace
01 SDK

请求进来，探针自动开 root span，生成 traceID 并写进日志上下文。

02 传播

traceparent 头随 HTTP / MQ 传下去，下游服务接上同一棵树。

03 导出

span 攒批后经 OTLP HTTP 发到 Gateway 4318，日志同步写进 stdout。

04 等待

Sampler 缓存 60 秒，等这条 trace 的 span 到齐，再决定留或丢。

05 落库

命中「有 ERROR」且「超过 2 秒」，整条链路被保留，可点开看瀑布图。

注意 60 秒是从收到第一个 span 开始算，不是请求结束后再等 60 秒。晚到的 span 可能继承已缓存的丢弃决定。
Zero-Code Injection

不改代码，探针是怎么进去的

关键在于 Kubernetes 的 准入 Webhook：Pod 还没启动，Operator 就已经把探针和配置写进了它的定义里。

01

提交 Deployment

Pod 模板上带一行 annotation，指向某个 Instrumentation 配置。

inject-java:
observability/standard
02

Webhook 拦截

控制面把 Pod 定义交给 Operator 的 Webhook，它改写 spec 后返回。

MutatingWebhook
failurePolicy: Ignore
03

initContainer 复制

新增初始化容器，把 agent 拷到共享空目录，并注入环境变量。

JAVA_TOOL_OPTIONS
+ -javaagent:/otel/…
04

应用照常启动

业务进程不知道自己被埋点了，只是多了些 span 和指标往外发。

OTEL_EXPORTER_OTLP_
ENDPOINT=…:4318
怎么算注入成功

看新 Pod 里有没有 initContainer，再看后端有没有数据。 只看 Deployment 上有 annotation 不算 注入成功。

唯一风险点

Webhook 故障时（默认 Ignore），Pod 会正常创建但没有探针 —— 业务不受影响， 但这段流量没有链路数据。所以必须对注入失败单独告警。

Tail Sampling

尾采样：先看完整条链路，再决定留不留

策略一

任意 span 状态 = ERROR

必须是 span 的 status，不是日志里出现「error」这几个字。SDK 没把 HTTP 500 标成 ERROR 时，要先修埋点。

策略二

链路耗时 ≥ 2000ms

配置里写 threshold_ms: 1999。固定版本按整数毫秒并用严格「>」， 填 2000 会漏掉正好 2 秒的请求。

策略三

约 10% 概率命中

不是「每十条留一条」。每条 trace 独立按概率决定，短期有波动；普通成功请求本来就可能被丢弃。

默认参数
decision_wait60s num_traces200000 / 分片 max_trace_size5 MiB decision_cache30万 + 30万
注意 尾采样只决定 trace 留不留。日志与指标走各自的 pipeline，不受采样影响 —— 所以「链路没了但日志还在」是正常现象。
Metrics Discovery

指标：谁去抓，怎么保证不重复抓

为什么需要 TA

两个 Scraper 如果各自发现全部目标，同一份指标会被抓两遍，后端出现重复序列。 Target Allocator 把目标集合做一致性哈希，每个目标只交给一个 Scraper。

发现什么

PodMonitor / ServiceMonitor / Probe / ScrapeConfig，加上平台自监控。只发现带 owner=otel 标签的 Monitor，不会误抓别的团队的对象。

指标标签必须补齐

把 Resource 属性按白名单复制到数据点：k8s_cluster_name、k8s_namespace_name、k8s_pod_name、k8s_container_name、service_name。 否则不同 Pod 的同名指标会在后端被合并成一条时间序列。

已有 Prometheus 若也在全选 Monitor，新增的 Monitor 会被两边同时发现 —— 上线前必须先划清发现范围。

怎么验收

在后端按集群、namespace、Pod 查 up，核对目标数量与副本数是否对得上； 再看一个真实业务指标的标签是否完整。Pod Ready 与平台自监控有数据，都不能证明业务 Monitor 发现成功。

Logs Pipeline

日志：从节点上的文件，到能点回链路

STEP 01

读文件

直接读宿主上的容器日志，含未压缩的轮转文件。

/var/log/pods/…/0.log 含轮转 0.log.2026… 排除 .gz / .tmp checkpoint → hostPath
STEP 02

拆外层

先剥掉 CRI 的时间与流标记，再还原被拆分的分片。

container parser 还原 CRI P / F 分片 区分 stdout / stderr 补时间与流标记
STEP 03

合多行

默认不合并，避免把相邻的独立日志拼成一条。

默认不合并 按 namespace / 容器 单独开首行规则 避免把独立日志拼错
STEP 04

提升关联 ID

把日志里的 ID 变成原生字段，日志才能点回链路。

trace_id / span_id 32 / 16 位 hex + level / timestamp 不凭空造 ID
// 推荐的单行 JSON { "timestamp": "2026-10-22T12:00:00.123+08:00", "level": "ERROR", "message": "inventory timeout", "trace_id": "4bf92f35…4736", "span_id": "00f067aa0ba902b7" }

两次验收，别混为一谈

① 能在后端查到日志 —— 证明采集通了。
② 点日志能跳到 trace —— 证明 ID 被解析成原生字段，且那条 trace 没被采样丢弃。

多行堆栈（Python traceback / Go panic）不能直接套日期首行规则，要先确认真实首行格式， 再按 namespace + 容器名开合并。采样丢弃后日志里仍会有合法 traceID，但点过去查不到链路 —— 这是正常边界。

Deployment · Step 1–4

部署：四条命令，一个维护窗口

01 准备

确认 context、节点数、后端地址与认证；复制一份集群 values，真实凭据不提交 Git。

02 装 Operator

先查是否已有实例；没有才装。它负责 CRD、Webhook 与探针注入。

03 装采集平台

两个 values 一起加载：处理规则 + 集群参数。默认无 PVC，队列在内存。

04 验收

Helm 返回成功 ≠ 可用。逐个工作负载确认 Ready，再查三要素有没有真实数据。

# 01 准备 kubectl config get-contexts cp values-platform.yaml "$OTEL_VALUES" # 02 安装 Operator（先确认没有已有实例） helm upgrade --install otel-operator ./charts/opentelemetry-operator-0.126.1.tgz \ --kube-context "$OTEL_CONTEXT" -n opentelemetry-operator-system \ --create-namespace -f values-operator.yaml --wait --timeout 10m # 03 安装采集平台 helm upgrade --install otel-platform ./charts/otel-platform-0.7.8.tgz \ --kube-context "$OTEL_CONTEXT" -n observability --create-namespace \ -f values-telemetry.yaml -f "$OTEL_VALUES" --wait --timeout 10m # 04 验收：Helm 成功之后还要逐个确认 kubectl -n observability get pods,pvc,instrumentations kubectl -n observability rollout status statefulset/otel-gateway-collector --timeout=5m

先接一个可灰度的服务 → 三要素验收通过 → 再按业务域分批。 当前版本完成的是低流量 Java 验证，不等于 200 个服务峰值已验收。

接入最常见的四个坑 · 先查什么
没有 initContainer

annotation 放错层级、只改了旧 Pod、Webhook 未生效

x509 证书错误

后端 / kubelet / Operator 三类 CA 不要混用，也别关校验

Trace 查不到

可能真的被 10% 采样丢了；先看 SDK 是否生成、60s 窗口是否已过

只有 Ready 没数据

Ready 只表示进程健康，要看出口错误、队列与三信号唯一标记

Capacity

容量：24 个节点，约 8.5 核 / 20.75 GiB

角色数量CPU req / limit内存 req / limit用途
Gateway2500m / 21024 / 2048 Mi接入 · 补全 · 路由
Sampler2500m / 22048 / 4096 Mi尾采样缓存最吃内存
Scraper2500m / 21024 / 2048 MiPrometheus 抓取
Cluster1500m / 2512 / 1024 Mi对象状态 · 事件
NodeN200m / 2512 / 1024 Mi日志 · 宿主指标
Target Allocator1200m / 1256 / 1024 Mi目标发现
Operator1200m / 1256 / 512 MiCRD · 注入

request 用于调度预算，limit 用于约束，都不是实测 RSS。不含业务探针与后端存储； 200 个服务不能直接换算成资源。

尾采样条数怎么算
新 trace/s × 60s × 余量

按每个 Sampler 的新 traceID 到达率算，同一条 trace 的多个服务 span 不能重复计入。

4000 新 trace/s · 60s · 2 副本 · 1.5 倍余量 → 每副本需 180,000 条

当前 200,000 条 / 副本，压测在 6,405 trace/s 下内存 852 Mi / 4096 Mi。

队列容量不是磁盘上限

每个 exporter 256 MiB 逻辑容量。5 MiB/s 的日志入口只够约 51 秒；要扛 10 分钟，理论就得 3000 MiB 起。 恢复吞吐必须大于持续输入才追得平。

Boundaries

说清楚：我们保证什么，不保证什么

可观测性平台最容易出问题的地方，不是采不到，而是以为采到了。

平台负责保证
采集层的可用性

多副本 + 拓扑分布 + PDB，单副本故障不中断接入

身份与关联的正确性

K8s 元数据、服务名、trace/span 字段按真实语义补全，不造假

有界缓冲与背压

队列容量明确、满则背压而非静默丢弃，磁盘可观测

异常可被发现

自监控覆盖队列、丢弃、拒收、证书到期，规则随平台交付

需要业务 / 项目方确认
采样窗口内的数据

60 秒窗外的迟到 span 不承诺补回；待决 trace 在内存，重启即丢

业务自定义指标

annotation 推不出业务 Counter，必须代码里埋点

任意框架零代码可用

自动埋点只覆盖上游支持的库；MQ、异步、自建协议需回归

后端是否真的落库

HTTP 200 只代表被接收；部分成功、Bulk 内失败要按后端契约验

上线前必须做的一件事
由项目负责人明确写下每条链路允许的数据缺口与恢复时间（RPO），并在测试环境演练一次： 后端 503、强制重建 Gateway / Sampler、磁盘接近满。演练结论写进验收报告。
